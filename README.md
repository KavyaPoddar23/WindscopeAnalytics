
# WindScope Analytics

### UK Wind Generation Forecast Accuracy & Energy Procurement Intelligence

WindScope Analytics is a full-stack web application designed to analyze historical wind power generation forecasts against actual electricity generation in Great Britain.

The application uses data from the **Elexon Balancing Mechanism Reporting Service (BMRS)** to evaluate day-ahead wind generation forecast accuracy, visualize generation trends, and calculate statistical error metrics.

The project demonstrates historical energy data processing, time-aware forecast selection, REST API development, and interactive data visualization.

## 1. Project Overview

Wind generation is an important component of Great Britain's electricity system. However, the amount of electricity generated by wind farms depends on weather conditions, making accurate forecasting essential for energy planning and procurement.

WindScope Analytics evaluates the accuracy of historical wind generation forecasts by comparing forecasted electricity generation with actual recorded generation.

The analysis focuses on **January 2026**, using a fixed day-ahead decision cutoff to ensure that only forecasts available at the relevant decision time are considered.

### Objectives

- Retrieve historical wind generation data from Elexon BMRS.
- Compare forecasted and actual wind electricity generation.
- Select forecasts using a consistent day-ahead cutoff.
- Calculate forecast accuracy and error metrics.
- Visualize historical generation patterns.
- Support filtering by decision date.
- Export analysis records as CSV.
- Provide analytics through a REST API.

## 5. Forecast Selection Methodology

The application uses a historical day-ahead forecast selection approach.

### Decision Cutoff

For each electricity delivery interval, the decision cutoff is defined as:

**12:00 UTC on the previous calendar day (D-1).**

For example:

| Delivery Date | Decision Cutoff |
|---------------|-----------------|
| 10 January 2026 | 9 January 2026, 12:00 UTC |
| 15 January 2026 | 14 January 2026, 12:00 UTC |
| 1 February 2026 | 31 January 2026, 12:00 UTC |

### Forecast Selection Rules

1. Identify the electricity delivery interval.
2. Calculate the corresponding decision cutoff.
3. Retrieve forecasts for that delivery interval.
4. Exclude forecasts published after the cutoff.
5. Select the latest forecast published on or before the cutoff.
6. Match the selected forecast with actual generation.
7. Calculate the forecast error.

This approach avoids **look-ahead bias**, since forecasts published after the decision cutoff cannot influence the historical analysis.

### Analysis Period

The supported decision-date period is:

**1 January 2026 – 1 February 2026**

The default dashboard filter starts on 2 January 2026 and ends on 1 February 2026.

All timestamps are processed using UTC.

## 6. Forecast Accuracy Metrics

Let:

- `Fᵢ` = Forecasted generation for interval i
- `Aᵢ` = Actual generation for interval i
- `n` = Number of matched intervals

### Forecast Error

```text
Errorᵢ = Fᵢ - Aᵢ
```

A positive error indicates overforecasting, while a negative error indicates underforecasting.

### Mean Absolute Error (MAE)

```text
MAE = (1/n) × Σ |Fᵢ - Aᵢ|
```

MAE measures the average absolute difference between forecasted and actual generation.

Unit: MW

### Root Mean Squared Error (RMSE)

```text
RMSE = √[(1/n) × Σ(Fᵢ - Aᵢ)²]
```

RMSE penalizes larger forecast errors more heavily.

Unit: MW

### Forecast Bias

```text
Bias = (1/n) × Σ(Fᵢ - Aᵢ)
```

Interpretation:

- Positive bias: Overall overforecasting.
- Negative bias: Overall underforecasting.
- Bias near zero: Limited average directional error.

### Mean Absolute Percentage Error (MAPE)

```text
MAPE = (100/n) × Σ |(Fᵢ - Aᵢ) / Aᵢ|
```

The implementation excludes intervals with zero actual generation when calculating MAPE.

The denominator therefore uses only intervals with nonzero actual generation.

Unit: Percentage (%)

### Mean Forecast and Mean Actual

```text
Mean Forecast = Σ Fᵢ / n

Mean Actual = Σ Aᵢ / n
```

Both metrics are expressed in MW.

## 9. Local Installation

### Step 1: Clone the Repository

```bash
git clone https://github.com/KavyaPoddar23/WindscopeAnalytics.git
cd WindscopeAnalytics
```

### Step 2: Configure the Backend

Navigate to the backend directory:

```bash
cd backend
```

Create a Python virtual environment:

```bash
python -m venv venv
```

Activate it on Windows PowerShell:

```powershell
.\venv\Scripts\Activate.ps1
```

For macOS or Linux:

```bash
source venv/bin/activate
```

Install backend dependencies:

```bash
pip install -r requirements.txt
```

### Step 3: Download Historical Data

Run:

```bash
python download_data.py
```

This script retrieves historical wind generation actuals and forecasts from Elexon BMRS.

The downloaded records are saved locally as:

```text
backend/data/actuals.json
backend/data/forecasts.json
```

An internet connection is required for the initial download.

### Step 4: Start the Backend

Run:

```bash
python -m uvicorn app.main:app --reload
```

The backend starts at:

```text
http://127.0.0.1:8000
```

API documentation:

```text
http://127.0.0.1:8000/docs
```

Health endpoint:

```text
http://127.0.0.1:8000/api/health
```

### Step 5: Configure the Frontend

Open a second terminal.

From the repository root:

```bash
cd frontend
```

Install dependencies:

```bash
npm install
```

For local development, the Vite configuration proxies `/api` requests to the backend running on port 8000.

You can therefore run the frontend without setting `VITE_API_URL` locally.

### Step 6: Start the Frontend

```bash
npm run dev
```

Open:

```text
http://localhost:5173
```

The dashboard should load the historical analytics once the backend is running and the required data files are available.

## 11. REST API Documentation

The FastAPI backend exposes the following endpoints.

### GET `/`

Returns basic application information.

Example response:

```json
{
  "application": "WindScope Analytics",
  "status": "running",
  "documentation": "/docs"
}
```

### GET `/api/health`

Checks whether the application is responding.

Example response:

```json
{
  "status": "ok"
}
```

### GET `/api/analysis`

Returns forecast accuracy metrics and matching historical generation records.

Supported query parameters:

| Parameter | Type | Description |
|-----------|------|-------------|
| `start_date` | YYYY-MM-DD | Beginning of decision date range |
| `end_date` | YYYY-MM-DD | End of decision date range |

Example request:

```http
GET /api/analysis?start_date=2026-01-02&end_date=2026-01-31
```

Example response structure:

```json
{
  "period": {
    "start": "2026-01-02",
    "end": "2026-01-31"
  },
  "methodology": {
    "decisionCutoff": "12:00 UTC on D-1",
    "forecastSelection": "Latest published before cutoff",
    "errorDefinition": "Forecast minus actual",
    "unit": "MW"
  },
  "metrics": {
    "count": 0,
    "mae": null,
    "rmse": null,
    "bias": null,
    "mape": null,
    "meanActual": null,
    "meanForecast": null
  },
  "records": []
}
```

The metrics and records shown above are an illustrative empty-result response. Actual values depend on the historical data and selected date range.

### API Error Handling

The backend includes validation for:

- Invalid date ranges.
- Unsupported historical periods.
- Missing historical data files.
- Invalid or conflicting forecast records.

The API returns structured error responses when an analysis request cannot be completed.

## 16. Design Considerations

### Avoiding Look-Ahead Bias

Only forecasts published on or before the historical decision cutoff are eligible for selection.

### UTC Timestamp Handling

Forecast publication times, delivery intervals, and decision cutoffs are normalized to UTC.

### Data Validation

The backend handles missing values, duplicate forecast records, and conflicting records during processing.

### Reproducible Analysis

The application uses a fixed historical analysis period and deterministic forecast selection rules.

### Separation of Concerns

The backend manages data processing and calculations, while the frontend handles presentation and user interaction.

### API-Based Architecture

The frontend communicates with the backend through REST endpoints, allowing independent development and deployment.

---

## 17. Limitations

- The analysis is restricted to the supported January 2026 decision period.
- The application is designed for historical analysis rather than real-time forecasting.
- Historical records must be downloaded before analysis.
- Only intervals with eligible forecasts and matching actual generation are included.
- MAPE excludes records where actual generation is zero.
- Backend deployment requires access to the historical JSON files.
- The application does not train a machine learning model or generate new forecasts.
